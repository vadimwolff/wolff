# WolffMsg

Веб-мессенджер: статический фронтенд + Supabase (PostgREST) в качестве бэкенда.
Работает в браузере телефона и компьютера, ставится на домашний экран как приложение (PWA).

Что умеет: регистрация и вход, личные чаты, группы и публичные каналы с
глобальным поиском, сквозное шифрование переписки, фото, реакции, статусы
доставки и прочтения, счётчики непрочитанного, закрепление и отключение звука,
шесть тем оформления, работа в офлайне (оболочка приложения кэшируется) и
автоматический выбор доступного адреса сервера.

---

## 1. Быстрый старт

### Шаг 1. База данных

Откройте свой проект в [Supabase](https://supabase.com) → **SQL Editor** → **New query**,
вставьте содержимое [`db/schema.sql`](db/schema.sql) и нажмите **Run**.

Скрипт безопасно выполняется и на уже существующей базе: ничего не удаляется,
добавляются недостающие таблицы (`chats`, `room_reads`), колонки каналов,
представление `chat_previews`, индексы и функции входа, поиска и подписок. Пароли после этого хранятся в виде
bcrypt-хеша, а старые пароли открытым текстом автоматически превращаются в хеш
при первом успешном входе.

В конце скрипт печатает отчёт — в колонке **«функций создано»** должно быть `7`:

| функций создано (нужно 7) | профилей в базе | сообщений в базе | anon может писать сообщения |
|---|---|---|---|
| 7 | 12 | 340 | 1 |

Если там `0`, посмотрите вкладку с сообщениями (NOTICE) — скрипт пишет, что
именно не получилось. Шаги, способные упасть на «грязных» данных (например
никнеймы, совпадающие без учёта регистра), обёрнуты в блоки с перехватом
ошибок: раньше одна такая строка откатывала всю установку, из-за чего
появлялась ошибка `permission denied for table profiles`. Повторяющиеся ники
скрипт разводит сам, дописывая номер (`vadim`, `vadim2`), — пароли и переписка
при этом сохраняются.

### Шаг 2. Публикация сайта

Ниже два способа. Их можно использовать одновременно — приложение само выберет
рабочий адрес сервера.

---

## 2. Вариант A — Vercel (рекомендуется для России)

На Vercel вместе с сайтом разворачивается функция `api/db/[...path].js`. Браузер
обращается только к домену самого сайта, а к Supabase ходит уже сервер Vercel.
Сторонние домены в браузере не участвуют вообще — если открывается сайт,
значит работает и переписка.

1. [vercel.com](https://vercel.com) → **Add New… → Project** → импортируйте этот репозиторий.
2. Framework Preset: **Other**. Build Command и Output Directory оставьте пустыми.
3. **Settings → Environment Variables** добавьте (значения — из Supabase → Settings → API):

   | Имя | Значение |
   |---|---|
   | `SUPABASE_URL` | `https://<ваш-проект>.supabase.co` |
   | `SUPABASE_ANON_KEY` | публичный ключ `anon` |

4. **Deploy**. Сайт открывается по адресу `https://<проект>.vercel.app`.

Проверить прокси: `https://<проект>.vercel.app/api/db/profiles?select=id&limit=1`
должен вернуть JSON (`[]` — это нормально).

---

## 3. Вариант B — GitHub Pages

1. **Settings → Pages → Build and deployment → Source: GitHub Actions**.
   Этот шаг обязателен и делается вручную: токен GitHub Actions не имеет прав
   создавать сайт Pages, поэтому до включения деплой падает с ошибкой
   `Create Pages site failed. Resource not accessible by integration`.
2. **Actions → Deploy to GitHub Pages → Run workflow** (или любой push в `main`) —
   workflow [`.github/workflows/pages.yml`](.github/workflows/pages.yml)
   опубликует сайт на `https://<логин>.github.io/<репозиторий>/`.

GitHub Pages отдаёт только статику, серверного прокси там нет, поэтому браузер
обращается к Supabase напрямую или через прокси. Если в вашей сети эти адреса
недоступны, укажите приложению рабочий адрес — см. следующий раздел.

---

## 4. Если что-то заблокировано (доступ из России)

Приложение не привязано к одному адресу API. При запуске оно по очереди
проверяет адреса из [`assets/config.js`](assets/config.js) и запоминает первый
ответивший:

1. `/api/db` — прокси на домене самого сайта (работает на Vercel);
2. прокси Cloudflare Worker;
3. Supabase напрямую.

Если все они недоступны, внизу появится красная плашка «Нет связи с сервером».
Нажмите **Настроить** (или **Настройки → Соединение**) и вставьте рабочий адрес,
например адрес вашего развёртывания на Vercel:

```
https://<проект>.vercel.app/api/db
```

Функция отдаёт заголовки CORS, поэтому сайт с GitHub Pages может работать через
неё. Тот же адрес можно передать ссылкой — он сохранится автоматически:

```
https://<логин>.github.io/<репозиторий>/?api=https://<проект>.vercel.app/api/db
```

Практические замечания:

- домены `*.workers.dev` и `*.supabase.co` у части российских провайдеров
  недоступны — надёжнее всего свой домен, привязанный к Vercel или к Cloudflare
  Worker (в Vercel: **Settings → Domains**);
- домен `*.github.io` обычно открывается, поэтому связка «GitHub Pages для сайта
  + Vercel для `/api/db`» даёт два независимых пути;
- внешние сервисы приложение не использует: аватары рисуются локально, шрифты
  системные, картинки хранятся в самой базе.

## 5. Каналы, поиск и шифрование

**Публичные каналы.** «＋» → «Создать канал»: название, короткая ссылка
(`@designcode`) и описание. Канал сразу виден всем в поиске, публиковать записи
может только автор — это проверяется не в интерфейсе, а триггером в базе, поэтому
запрет нельзя обойти, отправив запрос напрямую.

**Глобальный поиск.** Строка поиска на главном экране ищет одновременно среди
ваших чатов, публичных каналов и людей — как в Telegram. Один запрос к функции
`wm_search` вместо нескольких обращений к таблицам.

**Сквозное шифрование.** В меню чата → «Шифрование» задаётся секретный код.
Из кода и идентификатора комнаты выводится ключ AES-256 (PBKDF2-SHA256,
210 000 итераций); шифрование и расшифровка выполняются в браузере, на сервер
уходит только строка вида `wm1:…`. Код нужно передать собеседнику любым другим
способом — через этот же чат его отправлять бессмысленно.

Что это защищает: переписку от того, у кого есть доступ к базе или публичный
ключ приложения. Чего не защищает: от человека, который знает код, и от
подмены самого сайта — код и ключ живут в браузере, поэтому при выходе из
аккаунта они стираются, а на новом устройстве код вводится заново.

## 6. Частые проблемы

**«permission denied for table profiles» или «База ещё не готова принимать регистрацию».**
Функции `wm_register` / `wm_login` не видны REST-API. Чаще всего это значит, что
`schema.sql` не выполнился до конца — проверьте отчёт в конце скрипта (раздел 1).
Реже — PostgREST ещё не обновил кеш; приложение само повторяет попытку через
полторы секунды, а вручную кеш обновляется одной строкой:

```sql
notify pgrst, 'reload schema';
```

**«Нет связи с сервером».**
Ни один из адресов в [`assets/config.js`](assets/config.js) не отвечает. Нажмите
в плашке **Настроить** и посмотрите на кружки: зелёный — адрес работает, красный —
нет. Если все красные, разверните проект на Vercel (раздел 2) и укажите его
адрес `/api/db` в поле для своего прокси.

**Проект Supabase «уснул».**
На бесплатном тарифе проект приостанавливается после недели простоя. Откройте
его на supabase.com и нажмите **Restore project**.

## 7. Локальный запуск и тесты

Для разработки есть стенд, который поднимает статику и эмулирует Supabase REST
в памяти процесса — база и ключи не нужны:

```bash
npm run dev          # http://localhost:8123
npm test             # четыре набора сквозных тестов в Chromium
```

`npm test` прогоняет 50 проверок в четырёх наборах:

1. **Основной сценарий** двумя браузерными профилями: регистрация, вход,
   переписка в реальном времени, реакции, статусы прочтения, группы, поиск,
   закрепление, очистка истории, удаление чата, смена имени и пароля,
   поведение при недоступном сервере.
2. **Каналы, поиск и шифрование**: создание канала, глобальный поиск, подписка,
   запрет на запись подписчику, шифртекст на сервере, замок без кода, отказ
   расшифровать неверным кодом, мгновенная отрисовка из кэша, переключение
   адреса API, а также проверка, что узлы сообщений не пересоздаются при
   опросе сервера и не сбрасывается выделение текста.
3. **Совместимость со «старой» схемой** базы (только `profiles` и `messages`).
4. **Состояние базы сразу после `schema.sql`**, когда кеш REST-API ещё не
   видит функций входа.

Структура:

```
index.html                 разметка всех экранов
assets/config.js           адреса API и параметры опроса
assets/app.js              вся логика приложения
assets/crypto.js           шифрование сообщений (AES-GCM + PBKDF2)
assets/styles.css          стили, темы и анимации
sw.js                      service worker (кэш оболочки)
api/db/[...path].js        прокси к Supabase для Vercel
db/schema.sql              схема базы и функции входа
tools/                     локальный стенд и тесты
```

## 8. Что было исправлено

Исходный файл `wolffmsg2.html` в рабочее состояние не приводился точечно — логика
переписана, потому что часть ошибок была архитектурной. Основное:

**Не работало по существу**

- список чатов хранился только в `localStorage`: собеседник не видел чат, пока не
  добавлял вас вручную. Теперь чаты и участники лежат в таблице `chats`, а
  локальная копия осталась только как кэш и запасной вариант;
- в открытом чате не было опроса сервера — новые сообщения появлялись лишь после
  отправки своего. Добавлен инкрементальный опрос (новые сообщения, реакции,
  удаления, отметки о прочтении);
- счётчик непрочитанных `f.unread` никогда не заполнялся, а вёрстка галочек
  статуса существовала в CSS, но не использовалась;
- `openReactions` была объявлена дважды: вторая версия перетирала первую и
  вызывала несуществующую `addReaction` — реакции не ставились вообще;
- `toggleChatActions`, `muteChat`, `clearHistory` тоже были продублированы;
- удаление аккаунта обращалось к несуществующей таблице `/users`;
- `openSettings` открывала `#settings-page`, которого нет в разметке (страница
  называется `#page-settings`);
- кнопка регистрации показывала текст «Ещё нет аккаунта? Создать» вместо действия,
  а никнейм при регистрации не проверялся на занятость — появлялись дубликаты;
- `syncData` перерисовывала список, но `setInterval` продолжал работать после
  выхода из аккаунта.

**Надёжность и безопасность**

- текст сообщений и имена подставлялись в `innerHTML` без экранирования — любое
  сообщение с HTML ломало разметку или выполняло код. Теперь всё экранируется, а
  обработчики повешены делегированием вместо `onclick` со строками;
- пароль передавался в строке запроса и хранился открытым текстом. Появились
  функции `wm_register` / `wm_login` / `wm_set_password` с bcrypt; читать колонки
  с паролями клиентскому ключу запрещено на уровне прав;
- любая сетевая ошибка показывала «Ошибка соединения» и возвращала `null`, из-за
  чего вызывающий код падал дальше. Теперь ошибки типизированы, есть
  переподключение, перебор адресов и постоянная плашка о состоянии связи;
- фото уходило в базу целиком в base64 — большие файлы просто не отправлялись.
  Изображения масштабируются до 1280 px и сжимаются в JPEG;
- `me.name.split(...)`, `JSON.parse(localStorage…)` и обращения к элементам
  выполнялись без проверок и роняли скрипт на пустых значениях.

**Интерфейс**

- CSS содержал по три копии правил для `#context-bar`, `.reaction-picker`,
  `.reaction-badge` и конфликтующие блоки для страниц: `#page-settings` был
  одновременно `display:flex !important` и сдвинут за экран. Стили переписаны без
  дублей, переменная `--panel` определена во всех темах (раньше меню были
  прозрачными в стандартной теме);
- добавлены: разделители дат, автор сообщения в группах, просмотр фото на весь
  экран, многострочный ввод (Enter — отправить, Shift+Enter — перенос), поиск,
  собственные модальные окна вместо `prompt`/`confirm` (они блокируются в части
  мобильных браузеров), аппаратная кнопка «назад», локальные аватары вместо
  запросов к `ui-avatars.com`.

## 9. Ограничения

Приложение обращается к базе публичным ключом `anon` — это подходит для личного
проекта, но означает, что владелец ключа технически может прочитать переписку
через API. Пароли этим ключом недоступны, но сами сообщения не шифруются. Для
настоящей приватности нужен переход на Supabase Auth с политиками RLS по
`auth.uid()` — текущая схема к этому подготовлена (таблицы и связи не изменятся,
меняются только политики и способ входа).
