# WolffMsg

Веб-мессенджер: статический фронтенд + Supabase (PostgREST) в качестве бэкенда.
Работает в браузере телефона и компьютера, ставится на домашний экран как приложение (PWA).

Что умеет: регистрация и вход, личные чаты, группы и публичные каналы с
глобальным поиском, личный раздел «Избранное», чат с помощником WolffAI,
голосовые сообщения, звонки один на один, сквозное шифрование переписки по
умолчанию, ответы с цитатой (в том числе смахиванием), реакции с просмотром
авторов, профили пользователей, фото и видео, кликабельные ссылки, статус
«в сети» с возможностью скрыть его, статусы доставки и прочтения, счётчики непрочитанного, закрепление и отключение звука, звуковой
сигнал о новых сообщениях на компьютере, шесть спокойных тем оформления,
работа в офлайне (оболочка приложения кэшируется) и автоматический выбор
доступного адреса сервера.

---

## 1. Быстрый старт

### Шаг 1. База данных

Откройте свой проект в [Supabase](https://supabase.com) → **SQL Editor** → **New query**,
вставьте содержимое [`db/schema.sql`](db/schema.sql) и нажмите **Run**.

Скрипт безопасно выполняется и на уже существующей базе: ничего не удаляется,
добавляются недостающие таблицы (`chats`, `room_reads`), колонки каналов,
представление `chat_previews`, индексы и функции входа, поиска и подписок. Пароли после этого хранятся в виде
bcrypt-хеша, а старые пароли открытым текстом автоматически превращаются в хеш
при первом успешном входе.

Скрипт добавляет и таблицу вложений `attachments` — без неё фотографии будут
храниться по-старому, внутри сообщений, и чат с ними станет заметно тяжелее.

В конце скрипт печатает отчёт — в колонке **«функций создано»** должно быть `12`:

| функций создано (нужно 12) | профилей в базе | сообщений в базе | anon может писать сообщения |
|---|---|---|---|
| 12 | 12 | 340 | 1 |

Если там `0`, посмотрите вкладку с сообщениями (NOTICE) — скрипт пишет, что
именно не получилось. Шаги, способные упасть на «грязных» данных (например
никнеймы, совпадающие без учёта регистра), обёрнуты в блоки с перехватом
ошибок: раньше одна такая строка откатывала всю установку, из-за чего
появлялась ошибка `permission denied for table profiles`. Повторяющиеся ники
скрипт разводит сам, дописывая номер (`vadim`, `vadim2`), — пароли и переписка
при этом сохраняются.

### Шаг 2. Публикация сайта

Ниже два способа. Их можно использовать одновременно — приложение само выберет
рабочий адрес сервера.

---

## 2. Вариант A — Vercel (рекомендуется для России)

На Vercel вместе с сайтом разворачивается функция `api/db/[...path].js`. Браузер
обращается только к домену самого сайта, а к Supabase ходит уже сервер Vercel.
Сторонние домены в браузере не участвуют вообще — если открывается сайт,
значит работает и переписка.

1. [vercel.com](https://vercel.com) → **Add New… → Project** → импортируйте этот репозиторий.
2. Framework Preset: **Other**. Build Command и Output Directory оставьте пустыми.
3. **Settings → Environment Variables** добавьте (значения — из Supabase → Settings → API):

   | Имя | Значение |
   |---|---|
   | `SUPABASE_URL` | `https://<ваш-проект>.supabase.co` |
   | `SUPABASE_ANON_KEY` | публичный ключ `anon` |

4. **Deploy**. Сайт открывается по адресу `https://<проект>.vercel.app`.

Проверить прокси: `https://<проект>.vercel.app/api/db/profiles?select=id&limit=1`
должен вернуть JSON (`[]` — это нормально).

---

## 3. Вариант B — GitHub Pages

1. **Settings → Pages → Build and deployment → Source: GitHub Actions**.
   Этот шаг обязателен и делается вручную: токен GitHub Actions не имеет прав
   создавать сайт Pages, поэтому до включения деплой падает с ошибкой
   `Create Pages site failed. Resource not accessible by integration`.
2. **Actions → Deploy to GitHub Pages → Run workflow** (или любой push в `main`) —
   workflow [`.github/workflows/pages.yml`](.github/workflows/pages.yml)
   опубликует сайт на `https://<логин>.github.io/<репозиторий>/`.

GitHub Pages отдаёт только статику, серверного прокси там нет, поэтому браузер
обращается к Supabase напрямую или через прокси. Если в вашей сети эти адреса
недоступны, укажите приложению рабочий адрес — см. следующий раздел.

---

## 4. Если что-то заблокировано (доступ из России)

Приложение не привязано к одному адресу API. При запуске оно проверяет все
адреса из [`assets/config.js`](assets/config.js) одновременно и берёт первый
ответивший из списка приоритетов:

1. «Через сервер сайта» — `/api/db`, прокси на домене самого сайта (Vercel);
2. «Резервный канал» — прокси на стороннем домене;
3. «Основной сервер» — база напрямую.

В настройках показываются только эти названия и состояние каждого канала:
адреса на экран не выводятся.

Если все они недоступны, внизу появится красная плашка «Нет связи с сервером».
Нажмите **Настроить** (или **Настройки → Соединение**) и вставьте рабочий адрес,
например адрес вашего развёртывания на Vercel:

```
https://<проект>.vercel.app/api/db
```

Функция отдаёт заголовки CORS, поэтому сайт с GitHub Pages может работать через
неё. Тот же адрес можно передать ссылкой — он сохранится автоматически:

```
https://<логин>.github.io/<репозиторий>/?api=https://<проект>.vercel.app/api/db
```

Если адрес отказывает уже во время работы, приложение не ждёт таймаута на
каждом запросе: сбойный запрос тут же повторяется на следующем адресе, а
неудачник уходит на паузу с растущим интервалом (4 с, 8 с, 16 с… до двух минут)
и возвращается в строй, как только снова начинает отвечать. Ошибки 5xx и 429
считаются отказом адреса, а не ответом базы. В окне **Настройки → Соединение**
видно, какой адрес активен, сколько миллисекунд отвечает и кто на паузе.

Практические замечания:

- домены `*.workers.dev` и `*.supabase.co` у части российских провайдеров
  недоступны — надёжнее всего свой домен, привязанный к Vercel или к Cloudflare
  Worker (в Vercel: **Settings → Domains**);
- домен `*.github.io` обычно открывается, поэтому связка «GitHub Pages для сайта
  + Vercel для `/api/db`» даёт два независимых пути. В этой связке заполните ещё
  и `serverUrl` в [`assets/config.js`](assets/config.js) — адресом вида
  `https://<проект>.vercel.app`: на GitHub Pages серверной части нет, и без
  этого адреса не найдутся помощник WolffAI, уведомления при закрытом
  приложении и гифки;
- внешние сервисы приложение не использует: аватары рисуются локально, шрифты
  системные, картинки хранятся в самой базе.

## 5. Как устроен чат

**Экранная клавиатура.** Приложение измеряет её высоту через `visualViewport` и
поднимает интерфейс ровно на эту величину: поле ввода, кнопки и модальные окна
всегда остаются над клавиатурой, шапка чата — на месте. Все поля ввода имеют
шрифт 16 px, иначе iOS увеличивает страницу при фокусе. Когда клавиатура
открывается, список докручивается к последнему сообщению.

**Галочки.** Одна — сообщение сохранено на сервере, две — собеседник его
прочитал. Пока сообщение отправляется, вместо галочек показываются часики,
при ошибке — красная отметка.

**Фотографии и видео.** Снимок хранится отдельно от сообщения: в переписке
лежит только ссылка на него и крошечное превью в несколько килобайт. Поэтому
чат открывается мгновенно — сначала виден размытый кадр, затем он сам
заменяется полным. За один раз можно выбрать несколько снимков — уйдут по
очереди.

Видео перед отправкой пережимается прямо в браузере: кадры перерисовываются в
уменьшенный холст (до 640 px по большей стороне), звук берётся из самого
файла, и всё это заново записывается с разумным битрейтом. Телефон снимает по
20 Мбит/с — после сжатия минутный ролик весит около 7 МБ вместо 150. Сжатие
идёт в реальном времени, поэтому минутный ролик готовится примерно минуту, с
показом процентов. Предел — 3 минуты и 16 МБ готового файла. В переписке
остаются кадр-превью и длительность, сам ролик подгружается по нажатию и
открывается на весь экран. И превью, и сами файлы шифруются ключом чата.

**Гифки.** Кнопка «GIF» рядом со скрепкой открывает панель поиска. Найденная
гифка не вставляется ссылкой на чужой сервис: её скачивает ваш сервер,
приложение шифрует её ключом чата и отправляет обычным вложением. Поэтому
стороннему сервису не видно, кто и в каком чате что смотрит, а в переписке
место под гифку резервируется заранее — список не «прыгает», и загружаются
только те гифки, что попали на экран. Настройка — в разделе 11.

**Запись о звонке.** После разговора в переписке остаётся строка «📞 Звонок ·
1:23», а если не ответили — «Пропущенный звонок» или «Звонок отклонён». Пишет
её тот, кто звонил, поэтому запись всегда одна.

**Меню сообщения.** Открывается одним нажатием на сообщение — а также долгим
нажатием и правой кнопкой на компьютере: ряд эмодзи, «Ответить», «Копировать»,
«Кто отреагировал» и «Удалить» для своих сообщений. Нажатия на ссылку, фото,
видео, голосовое, плашку реакции, цитату и имя автора работают по-своему и
меню не открывают.

**Удаление с подтверждением.** «Удалить» в меню сначала спрашивает ещё раз —
случайное нажатие переписку не портит.

**Ответ смахиванием.** Сообщение смахивают влево — открывается ответ на него.
Чтобы это не срабатывало случайно, засчитывается только движение пальцем,
заметно горизонтальное и доведённое до порога; любое движение вверх-вниз
сразу отменяет жест — это прокрутка. Мышью смахивание не работает вовсе.

**Одна реакция от человека.** Новая реакция заменяет предыдущую, повторное
нажатие на ту же — снимает её. Нажатие на плашку с реакцией ставит такую же
реакцию (или снимает свою), а посмотреть, кто отреагировал, можно в меню
сообщения — пункт «Кто отреагировал». В каналах список авторов не показывается.

**Ссылки.** Адреса в тексте становятся кликабельными и открываются в новой
вкладке; остальной текст остаётся обычным. Хвостовые точки и скобки в адрес не
попадают, а почтовый адрес ссылкой не становится. Открываются только адреса
http и https — ничего другого выполнить через сообщение нельзя.

**Голосовые сообщения.** Пока в поле ничего не набрано, вместо «отправить»
стоит микрофон. Короткое нажатие включает запись и оставляет её включённой
(рядом появляются «Отмена» и «Отправить»), удержание записывает, пока держат
палец, движение влево — отмена. Запись шифруется ключом чата и уходит
отдельным вложением, а в переписке остаётся полоса воспроизведения с
длительностью. Максимум — три минуты.

**Ответы.** Цитата хранится вместе с сообщением, поэтому отображается сразу, без
дополнительных запросов. В зашифрованном чате цитата шифруется так же, как текст.
Нажатие на цитату подсвечивает исходное сообщение.

**Прокрутка.** При входе в чат всегда виден конец переписки — даже если
фотографии догружаются уже после открытия. Дальше список сам никуда не уезжает. Он прокручивается вниз
только при открытии чата, при отправке своего сообщения или если вы и так внизу.
Когда вы читаете историю, о новых сообщениях сообщает кнопка со счётчиком в углу,
а место, на котором вы остановились, не меняется. Граница непрочитанного
отмечается отдельной чертой.

**Профили.** Открываются из шапки личного чата, по имени автора в группе, из
списка авторов реакций и из настроек. В группе и канале шапка показывает состав
участников.

**Системная строка телефона.** Время, заряд и сеть стоят на собственной
полосе поверх приложения: раньше они сливались с шапкой. Цвет полосы меняется
вместе с темой, а в обычном браузере её просто нет.

**Виброотклик.** Короткий и почти незаметный — он подсказывает, что нажатие
засчитано, и не «бьёт по руке». Заметная вибрация осталась только у входящего
звонка, и та мягким пунктиром.

**«В сети».** Приложение раз в минуту отмечает присутствие в профиле, и в
шапке личного чата видно «в сети» или «был(а) в 14:05». Это можно скрыть:
Настройки → «Показывать, что я в сети» — тогда другие видят только имя. В базе
для этого две колонки, `last_seen` и `show_online`; роль приложения может
менять их только у профилей и не получает доступа ни к чему другому.

**«Избранное».** Личный раздел, который всегда стоит первым в списке чатов:
заметки, ссылки и фотографии для себя. Это комната, в которой один участник, а
её ключ зашифрован только вашим собственным ключом — прочитать записи не может
ни другой пользователь, ни сервер. Раздел создаётся сам при первом запуске,
удалить его нельзя (историю внутри — можно).

**Поиск.** Строка поиска разворачивается в отдельный экран: шапка уступает
место полю ввода с кнопкой «Отмена», а результаты идут разделами — «Ваши чаты»,
«Каналы», «Люди» и «Сообщения». Поиск по сообщениям выполняется на самом
устройстве, по уже расшифрованной переписке: запрос никуда не отправляется, а
найденное слово подсвечивается. Последние запросы сохраняются и повторяются
одним нажатием.

**Звук новых сообщений.** На компьютере при сообщении в неоткрытом чате звучит
короткий мягкий сигнал из двух нот. Он собирается прямо в браузере, поэтому
ничего не скачивается; между сигналами выдерживается пауза, чтобы поток
сообщений не превращался в трель. Отключается в Настройках → «Звук новых
сообщений»; в отключённых (🔇) чатах не звучит вовсе.

## 6. Каналы, поиск и шифрование

**Публичные каналы.** «＋» → «Создать канал»: название, короткая ссылка
(`@designcode`) и описание. Канал сразу виден всем в поиске, публиковать записи
может только автор — это проверяется не в интерфейсе, а триггером в базе, поэтому
запрет нельзя обойти, отправив запрос напрямую.

**Вход в канал не подписывает.** Из поиска канал открывается на просмотр:
записи видны, а внизу ждёт кнопка «Подписаться». Пока её не нажали, канал не
появляется в списке чатов и счётчик подписчиков не растёт.

**Состав подписчиков закрыт.** В карточке канала видно только их число —
списка участников в интерфейсе нет ни у кого, включая автора.

**Обсуждения под записями.** У каждой записи внизу есть строка «Комментировать»
или счётчик комментариев. Нажатие открывает отдельную ветку, где писать может
любой подписчик, а не только автор. Технически это отдельная комната
`post_<номер записи>`, поэтому запрет на публикацию в самом канале её не
касается, а в списке чатов она не появляется. Возврат из обсуждения ведёт
обратно в канал.

**Глобальный поиск.** Строка поиска на главном экране ищет одновременно среди
ваших чатов, публичных каналов и людей. Это один запрос к функции `wm_search`
вместо нескольких обращений к таблицам.

**Сквозное шифрование — по умолчанию, ничего настраивать не нужно.**

Как это устроено:

1. При регистрации браузер создаёт пару ключей ECDH P-256. Открытый ключ
   попадает в профиль, закрытый шифруется ключом из пароля (PBKDF2-SHA256,
   210 000 итераций) и только в таком виде хранится на сервере.
2. У каждого личного чата и каждой группы свой случайный ключ AES-256-GCM.
   Он шифруется отдельно для каждого участника общим секретом ECDH и лежит в
   таблице `room_keys` — без закрытого ключа участника эта строка бесполезна.
3. Сообщения, цитаты, фотографии и подписи в списке чатов шифруются ключом
   чата. На сервере остаются строки вида `wm1:…`.

Пароль не покидает устройство: на сервере лежит только его bcrypt-хеш, а
закрытый ключ проверяющей стороне недоступен даже на чтение — колонки
`enc_private_key` и `key_salt` не выдаются в запросах к таблице, их возвращает
только функция входа своему владельцу. При входе на новом устройстве ключ
восстанавливается из этой зашифрованной копии по паролю.

**Где лежит закрытый ключ на самом устройстве.** В собственной базе браузера
(IndexedDB) как «неизвлекаемый» объект: расшифровывать им можно, а выгрузить
его содержимое нельзя — ни расширению, ни постороннему коду на странице. Ключ,
сохранённый прошлой версией в обычном хранилище, переносится туда при первом
запуске, а старая копия стирается. Рядом хранится копия ключа, зашифрованная
паролем: она нужна только для смены пароля и без пароля бесполезна.

**Смена пароля не теряет переписку.** При смене пароля закрытый ключ
перешифровывается новым паролем и обновляется на сервере. Раньше он оставался
зашифрованным старым паролем, и вход на другом устройстве с новым паролем
приводил к выдаче новой пары ключей — вся прежняя переписка становилась
нечитаемой.

**Чужой сервер по ссылке.** Адрес сервера можно передать параметром `?api=`.
Если он ведёт на другой домен, приложение сначала спрашивает разрешение и
показывает, куда именно уйдут сообщения и пароль: иначе достаточно было бы
прислать ссылку, чтобы увести переписку на посторонний сервер.

**Страница исполняет только свои скрипты.** Заголовок `Content-Security-Policy`
запрещает выполнение любого стороннего кода и загрузку чужих ресурсов, поэтому
текст сообщения не может стать программой.

**Адреса серверов не показываются.** В настройках соединения видны только
названия каналов связи и их состояние; сохранённый вами адрес не выводится на
экран — убрать его можно кнопкой «Сбросить».

**Ключи не попадают в браузер.** Ключ Gemini и закрытый ключ уведомлений лежат
только в настройках сервера. Ключ базы нужен лишь прямым адресам: когда
приложение работает через свой сервер (`/api/db`), запросы уходят вообще без
ключа — его подставляет сам сервер. Чтобы убрать ключ из браузера полностью,
смените его в Supabase (**Settings → API → rotate anon key**), пропишите новый
только в переменных Vercel и оставьте `apiKey` в
[`assets/config.js`](assets/config.js) пустым: тогда останется единственный
путь — через ваш сервер, и в исходниках страницы ключей не будет вовсе.

**Код безопасности.** В меню чата → «Шифрование» показан код, посчитанный из
двух открытых ключей. Если он совпадает у обоих собеседников, ключи не
подменены. Сверьте его при встрече или по другому каналу.

Что остаётся видно владельцу базы: никнеймы, имена и аватары (это визитка,
по которой вас находят), а также кто, когда и в каком чате писал — сами тексты
при этом нечитаемы. Каналы публичные по своей природе и не шифруются:
подписаться может любой, поэтому шифровать записи было бы самообманом.

## 7. Установка приложения и уведомления

**Установка.** Настройки → «Установить приложение» открывает окно с пошаговой
инструкцией. Устройство определяется само, но вкладки вверху позволяют
посмотреть инструкцию и для другого — например, чтобы продиктовать её кому-то.

- **Android (Chrome):** появится системный диалог — нажмите «Установить».
- **iPhone (Safari):** «Поделиться» → «На экран «Домой»» → «Добавить».
  Системного диалога в iOS нет, приложение показывает эти шаги само.
- **Компьютер (Chrome, Edge):** значок установки в адресной строке или
  меню браузера → «Установить приложение».

Файл `manifest.webmanifest` лежит в корне сайта, а не в подпапке: `start_url` и
`scope` считаются от адреса самого манифеста, поэтому из подпапки ярлык
приложения открывал бы несуществующий адрес и браузер показывал бы «404».
На случай, если такой ярлык уже сохранён, рядом лежит `404.html` — он
переводит на главную вместе с адресом чата из уведомления.

После установки WolffMsg открывается без адресной строки, с собственной
иконкой и запоминает вход.

**Уведомления.** Настройки → «Уведомления» → разрешить. Дальше приложение
показывает уведомление о сообщении в любом чате, кроме открытого; нажатие
открывает нужный чат и подсвечивает сообщение. На значке приложения
показывается число непрочитанных.

**Значок в строке состояния.** Телефон рисует значок уведомления одним цветом,
беря от картинки только её прозрачность: цветная иконка приложения
превращалась там в белый квадрат. Поэтому для строки состояния сделан
отдельный одноцветный силуэт [`assets/badge.svg`](assets/badge.svg) →
`assets/badge-96.png` (пересобирается командой `node tools/make-icons.mjs`).

## 8. Уведомления при полностью закрытом приложении

Пока приложение запущено или свёрнуто, уведомления показывает оно само. Чтобы
сообщения доходили и при закрытом приложении, нужен сервер, который разошлёт
их через службу доставки браузера (Google, Apple, Mozilla). Такой сервер уже
написан — это функция [`api/push.mjs`](api/push.mjs) рядом с прокси базы.

**Что сделать один раз:**

1. Выполните [`db/schema.sql`](db/schema.sql) заново — он добавит таблицу
   подписок и три функции. В отчёте должно быть `11` функций.
2. Разверните проект на Vercel (раздел 2), если он ещё не развёрнут: на
   GitHub Pages серверной части нет.
3. Получите пару ключей: `node tools/vapid-keys.mjs` (или возьмите любую
   пару ключей VAPID).
4. Vercel → **Settings → Environment Variables** добавьте:

   | Имя | Значение |
   |---|---|
   | `VAPID_PUBLIC_KEY` | открытый ключ из скрипта |
   | `VAPID_PRIVATE_KEY` | закрытый ключ из скрипта |
   | `VAPID_SUBJECT` | `mailto:ваша-почта@example.com` |

5. **Redeploy**. Проверить: `https://<проект>.vercel.app/api/push` должен
   ответить `{"ok":true,"vapid":"…"}`.
6. В приложении: Настройки → «Уведомления» → разрешить. Если сервер найден,
   появится подпись «приходят и при закрытом приложении».

Открытый ключ вписывать никуда не нужно: приложение забирает его с сервера
само. Адрес сервера тоже ищется автоматически — рядом с адресом базы
(`…/api/db` → `…/api/push`) и на домене самого сайта. Если сайт открыт с
GitHub Pages, серверной части на нём нет: заполните `serverUrl` в
[`assets/config.js`](assets/config.js) адресом вида
`https://<проект>.vercel.app` (или укажите его один раз на устройстве:
Настройки → «Помощник WolffAI» → «Указать адрес»). Один адрес включает сразу
и помощника, и рассылку уведомлений, и гифки.

**Как это работает.** Отправив сообщение, приложение просит сервер разослать
уведомление и передаёт только его номер. Сервер спрашивает базу, кому это
сообщение адресовано: функция `wm_push_targets` сама проверяет, что сообщение
настоящее и написано только что, поэтому послать уведомление «просто так»
через неё нельзя. Текст никуда не передаётся и на сервере не
расшифровывается — в уведомлении видно только имя отправителя. Таблица
подписок закрыта полностью: ни прочитать чужие адреса, ни записать их
напрямую нельзя.

Уведомление не показывается, если приложение открыто на экране (там уже есть
свои уведомления и звук) или если чат отключён (🔇) — настройки чатов
приложение дублирует в базу браузера, откуда их читает service worker.

**Чего это не делает.** На iPhone уведомления при закрытом приложении работают
только если сайт добавлен на экран «Домой» (iOS 16.4+) — в обычной вкладке
Safari их не будет. Это ограничение самой iOS, а не приложения.

## 9. WolffAI — помощник в отдельном чате

Чат с WolffAI появляется у каждого сам, сразу под «Избранным». Отвечает Gemini
от Google: у него есть бесплатный лимит, которого хватает для личного
пользования.

**Куда вставить ключ.**

1. Получите ключ на [aistudio.google.com/apikey](https://aistudio.google.com/apikey)
   («Create API key»). Ключ бесплатный.
2. Vercel → ваш проект → **Settings → Environment Variables** → **Add**:

   | Имя | Значение |
   |---|---|
   | `GEMINI_API_KEY` | ключ из Google AI Studio |

3. **Redeploy**. Проверить: `https://<проект>.vercel.app/api/ai` должен ответить
   `{"ok":true,...}`.

Ключ остаётся на сервере и в браузер не попадает.

**Если сайт открывают не с Vercel.** Помощник живёт на сервере, а на GitHub
Pages серверной части нет вовсе — там только файлы. Поэтому, когда приложение
открывают по адресу `https://<логин>.github.io/<репозиторий>/`, помощника
нужно один раз показать. Есть два способа, любой на выбор:

* **Раз и навсегда для всех.** В файле `assets/config.js` заполнить поле
  `serverUrl` адресом проекта:

  ```js
  serverUrl: "https://<проект>.vercel.app",
  ```

  После этого помощник, уведомления при закрытом приложении и гифки работают
  у всех и на всех устройствах, откуда бы сайт ни открывали.

* **На своём устройстве.** Настройки → «Помощник WolffAI» → «Указать адрес» →
  вставить `https://<проект>.vercel.app`. Приложение запомнит адрес и будет
  брать оттуда и помощника, и уведомления, и гифки.

**Если помощник не отвечает.** Настройки → «Помощник WolffAI» показывает
состояние: «подключён» или «не найден». Нажатие проверяет заново и показывает,
какие адреса были проверены и что там оказалось. Чаще всего причина одна из
трёх:

1. сайт открыт с GitHub Pages, а адрес сервера не указан — см. выше;
2. `GEMINI_API_KEY` добавлен, но не сделан **Redeploy** — переменные окружения
   применяются только к новой сборке;
3. проект не развёрнут на Vercel — тогда серверной части просто нет.

Прямая проверка сервера: откройте `https://<проект>.vercel.app/api/ai` — там
должно быть `{"ok":true,...}`. Если `{"ok":false}` — ключа нет в переменных
окружения или не было Redeploy.

**Запасные модели.** Сервер перебирает модели по очереди и переходит к
следующей, как только у текущей кончается бесплатный лимит (ответ 429) или она
недоступна. По умолчанию это `gemini-2.5-flash`, `gemini-2.5-flash-lite`,
`gemini-2.0-flash`, `gemini-2.0-flash-lite`; свой список можно задать
переменной `GEMINI_MODELS` через запятую. Если не ответила ни одна, в чат
приходит честное «сейчас большой спрос на WolffAI — он временно не работает».

**Позвать помощника в любой чат.** Достаточно написать в сообщении
`@WolffAI` — ответ придёт прямо в этот чат или группу, добавлять помощника в
участники не нужно. Ответ видят все участники, потому что он шифруется тем же
ключом чата.

**Приватность.** Переписка с помощником хранится так же зашифрованной, как
остальная: ключ есть только у вас, и чужой чат с WolffAI недоступен даже
владельцу базы. Но сам вопрос, чтобы получить ответ, отправляется на сервер и
дальше в Gemini — это единственное место, где текст покидает устройство в
открытом виде. Фотографии и голосовые помощнику не отправляются: на них он
отвечает, что понимает только текст.

## 10. Звонки

Звонок начинается кнопкой 📞 в шапке личного чата. Разговор идёт **напрямую
между устройствами** (WebRTC) и шифруется самим протоколом; база нужна только
чтобы стороны договорились — через таблицу `calls` передаются предложение,
ответ и сигнал завершения, и даже они зашифрованы ключом чата. Голос через
сервер не проходит и нигде не сохраняется.

На экране звонка есть выключение микрофона и завершение; у входящего —
«ответить» и «отклонить». Если собеседник не берёт трубку 45 секунд, звонок
сам завершается. Пока приложение свёрнуто, о входящем звонке приходит
уведомление.

**Звонок при закрытом приложении.** Если настроены уведомления (раздел 8),
входящий вызов приходит push-уведомлением, которое не гаснет само; по нажатию
приложение открывается и сразу показывает экран вызова. Без настроенных
уведомлений звонок увидит только тот, у кого приложение открыто или свёрнуто.

**Экран не гаснет** во время разговора, а после него в переписке остаётся
запись: «📞 Звонок · 1:23», «Пропущенный звонок» или «Звонок отклонён».

**Что нужно от вас:** ничего, кроме обновлённой базы (таблицы `calls` из
`db/schema.sql`) и разрешения на микрофон в браузере.

**Чего сайт не может.** Двух вещей на веб-странице сделать нельзя, и это
ограничение самих браузеров, а не приложения:

- **вывести звук в верхний (разговорный) динамик** — веб-странице недоступен
  выбор динамика, звонок идёт через основной. Помогают проводные или
  Bluetooth-наушники: их система выбирает сама;
- **гасить экран при поднесении телефона к уху** — датчик приближения сайтам
  не отдаётся, и управлять подсветкой экрана страница не может. Приложение
  делает противоположное доступное: не даёт экрану гаснуть во время разговора.

Обе возможности требуют настоящего приложения для Android/iOS.

**Честное ограничение.** Устройства ищут друг друга через публичные
STUN-серверы (список в [`assets/config.js`](assets/config.js)). В большинстве
сетей этого достаточно, но в некоторых — со «строгим» NAT, в части мобильных
сетей — прямое соединение не устанавливается: для таких случаев нужен
TURN-сервер, который пересылает звук через себя. Его адрес добавляется в тот же
список `iceServers` в виде `{ urls, username, credential }`. Бесплатных
надёжных TURN-серверов не бывает, поэтому по умолчанию его нет.

Звонки — только голосовые и только один на один: видео и групповые звонки не
делались.

## 11. Гифки

Гифки работают двумя способами, и первый не требует вообще ничего.

**Со своего телефона — без всяких ключей.** 📎 → выбрать файл `.gif`. Он уходит
живым, а не превращается в неподвижную картинку: гифки до 8 МБ отправляются как
есть (более тяжёлая уйдёт снимком). Шифруется так же, как фотография.

**Поиск гифок** (кнопка «GIF» рядом с полем ввода) идёт через ваш сервер:
приложение не обращается к чужому сервису напрямую, поэтому ключ остаётся на
сервере, а сервису не видно, кто и что ищет. Нужен ключ одного из двух сервисов —
любого:

| Имя | Где взять | Сложность |
|---|---|---|
| `GIPHY_API_KEY` | [developers.giphy.com](https://developers.giphy.com/) → Create an App → API Key | выдаётся сразу, бесплатно |
| `TENOR_API_KEY` | Google Cloud → включить **Tenor API** в проекте → создать ключ | нужен проект в Google Cloud |

Проще всего Giphy. С Tenor есть подвох: обычный ключ из AI Studio (тот, что для
Gemini) сам по себе не работает — в том же проекте Google Cloud должен быть
отдельно включён **Tenor API**, иначе сервис отвечает `403`. Именно поэтому
ключ Tenor часто «не работает».

1. Vercel → **Settings → Environment Variables** → добавить `GIPHY_API_KEY`
   (или `TENOR_API_KEY`).
2. **Redeploy**. Проверка: `https://<проект>.vercel.app/api/gif` должен вернуть
   `{"ok":true,...}`. Если `{"ok":false,...}`, в поле `detail` написано, что
   именно не так.

Заданы оба ключа — сначала пробуется Giphy, Tenor остаётся запасным.

**Если поиск не работает.** Настройки → «Поиск гифок» показывает состояние и по
нажатию объясняет причину теми же словами, что ответил сервис («ключ не принят»,
«превышен бесплатный лимит», «ключ не задан на сервере»).

Выбранная гифка не остаётся ссылкой на чужой сайт: её скачивает ваш сервер,
приложение шифрует её ключом чата и отправляет обычным вложением. В переписке
загружаются только те гифки, что попали на экран, а место под них
резервируется заранее — список не дёргается.

## 12. Частые проблемы

**«Не удалось выбрать лучшую функцию-кандидат».**
В базе остались две версии одной функции: `create or replace` не заменяет
функцию, у которой изменился набор параметров, а добавляет вторую. Выполните
[`db/schema.sql`](db/schema.sql) заново — он удаляет прежние версии перед
созданием новых. Увидеть дубли можно в нижней таблице
[`db/check.sql`](db/check.sql).

**Не создаются каналы.**
Выполните [`db/check.sql`](db/check.sql) в SQL Editor — он покажет таблицей, чего
не хватает. Каналам нужны функция `wm_create_channel`, колонки `chats.slug`,
`chats.owner_id`, `chats.is_public`, `chats.subscribers` и функции `wm_join_chat`,
`wm_leave_chat`, `wm_search`. Всё это создаёт `db/schema.sql`; после его
выполнения в проверке не должно остаться ни одного «НЕТ».

**«permission denied for table profiles» или «База ещё не готова принимать регистрацию».**
Функции `wm_register` / `wm_login` не видны REST-API. Чаще всего это значит, что
`schema.sql` не выполнился до конца — проверьте отчёт в конце скрипта (раздел 1).
Реже — PostgREST ещё не обновил кеш; приложение само повторяет попытку через
полторы секунды, а вручную кеш обновляется одной строкой:

```sql
notify pgrst, 'reload schema';
```

**«Нет связи с сервером».**
Ни один из адресов в [`assets/config.js`](assets/config.js) не отвечает. Нажмите
в плашке **Настроить** и посмотрите на кружки: зелёный — адрес работает, красный —
нет. Если все красные, разверните проект на Vercel (раздел 2) и укажите его
адрес `/api/db` в поле для своего прокси.

**Supabase пишет «Security Definer View» про `public.chat_previews`.**
Представление, из которого берутся подписи в списке чатов, по умолчанию
обращается к таблице сообщений от имени владельца базы, а не от имени того, кто
спрашивает, — то есть смотрит мимо политик доступа. В нынешней схеме политика
сообщений всё равно разрешает чтение всем (переписка защищена шифрованием, а не
политикой), поэтому утечки из-за этого нет, но проверка права: правило должно
быть одно для всех. Выполните [`db/schema.sql`](db/schema.sql) заново — он
включает представлению `security_invoker`, и предупреждение исчезает. Проверить
можно нижней таблицей [`db/check.sql`](db/check.sql): у `chat_previews` должно
стоять `security_invoker=on`.

**Проект Supabase «уснул».**
На бесплатном тарифе проект приостанавливается после недели простоя. Откройте
его на supabase.com и нажмите **Restore project**.

## 13. Локальный запуск и тесты

Для разработки есть стенд, который поднимает статику и эмулирует Supabase REST
в памяти процесса — база и ключи не нужны:

```bash
npm run dev          # http://localhost:8123
npm test             # пятнадцать наборов проверок
```

`npm test` прогоняет 182 проверки в пятнадцати наборах:

1. **Основной сценарий** двумя браузерными профилями: регистрация, вход,
   переписка в реальном времени, реакции, статусы прочтения, группы, поиск,
   закрепление, очистка истории, удаление чата, смена имени и пароля,
   поведение при недоступном сервере.
2. **Каналы, поиск и шифрование**: создание канала, глобальный поиск, подписка,
   запрет на запись подписчику, шифртекст на сервере, замок без кода, отказ
   расшифровать неверным кодом, мгновенная отрисовка из кэша, переключение
   адреса API, а также проверка, что узлы сообщений не пересоздаются при
   опросе сервера и не сбрасывается выделение текста.
3. **Реакции, ответы, профиль и прокрутка**: одна реакция от человека, список
   авторов реакций (и его отсутствие в каналах), ответ с цитатой и переход к
   исходному сообщению, профиль из шапки и из списка реакций, шесть тем,
   а также проверка, что чат не прокручивается сам, пока читаешь историю.
4. **Шифрование и надёжность соединения**: ключи создаются при регистрации,
   закрытый ключ не читается из таблицы, переписка и фотографии уходят на
   сервер шифртекстом, собеседник читает их без единой настройки, коды
   безопасности совпадают, вход на новом устройстве восстанавливает ключ по
   паролю, посторонний ключа не получает; плюс переключение адреса при отказе
   активного и переживание ошибки 503.
5. **Клавиатура и обсуждения в каналах**: поле ввода и модальные окна над
   клавиатурой, шапка на месте, интерфейс помещается на низком экране,
   комментарии под записью от нескольких человек, счётчик комментариев,
   возврат в канал и отсутствие обсуждений в списке чатов.
6. **Галочки, фотографии, каналы и уведомления**: одна галочка после отправки
   и две после прочтения, снимок уходит отдельным зашифрованным вложением,
   у собеседника сразу появляется превью, вход в чат показывает конец
   переписки, вход в канал не подписывает, состав подписчиков не виден,
   манифест и иконки готовы к установке, уведомление ведёт в нужный чат.
7. **Запуск, поиск, установка, избранное и звук**: адрес запуска из манифеста
   ведёт в приложение (та самая причина «404»), страница-спасатель возвращает
   на главную, поиск разворачивается в отдельный экран и закрывается «Отменой»,
   недавние запросы повторяются одним нажатием, «Избранное» стоит первым и
   уходит на сервер шифртекстом, чужой раздел недоступен, окно установки
   показывает шаги для трёх устройств, в настройках не видно адресов серверов,
   звук включается и не звучит очередью, а ссылка с чужим сервером требует
   подтверждения.
8. **Значок уведомления и доставка при закрытом приложении**: значок для
   строки состояния — прозрачный одноцветный силуэт, а не белый квадрат
   (проверяется по точкам картинки); приложение находит сервер рассылки,
   после отправки сообщения просит его разослать уведомление, адресатом
   оказывается собеседник, а не автор, и по выдуманному номеру сообщения
   рассылки не происходит.
9. **Ссылки, свайп, реакции, голос, WolffAI и звонки**: кликабельны только
   адреса (почтовый адрес и разметка — нет), смахивание влево открывает ответ,
   а короткое или вертикальное движение — нет; нажатие на плашку ставит такую
   же реакцию, список отреагировавших открывается из меню; голосовое
   записывается, уходит зашифрованным и слушается собеседником; чат с WolffAI
   есть у каждого, отвечает, хранится зашифрованным и недоступен другим, а при
   исчерпанном лимите честно сообщает о спросе; звонок между двумя браузерами
   действительно соединяется, звук приходит, сигналы на сервере зашифрованы, и
   завершение у одного закрывает звонок у обоих.
10. **Статусы, меню, удаление, видео и ключи**: «в сети» видно собеседнику и
   пропадает после выключения переключателя; одно нажатие открывает меню, а
   нажатие на реакцию — нет; удаление спрашивает подтверждение и по отказу
   ничего не удаляет; несколько снимков уходят за один выбор; видео
   отправляется с превью, шифруется и открывается на весь экран; через свой
   сервер ключ базы в запросах не появляется, а адрес помощника выводится из
   всех известных адресов сервера.
11. **Гифки, запись о звонке и строка состояния**: под системной строкой
   телефона есть своя полоса нужной высоты и цвета, цвет меняется вместе с
   темой; виброотклик не длиннее 10 мс; панель гифок ищет, не занимает пол-экрана
   и грузит превью через свой сервер; гифка уходит зашифрованным вложением с
   зарезервированным местом; сообщение с чужим ключом не показывается, а вместо
   него одна спокойная строка; «@WolffAI» получает ответ прямо в обычном чате;
   после звонка в переписке остаётся запись с длительностью, и отклонение
   закрывает звонок у обоих.
12. **Сайт и сервер на разных адресах, гифки без ключа**: приложение,
   открытое там, где серверной части нет (как на GitHub Pages), честно
   показывает «не найден» и перечисляет проверенные адреса; адрес сервера
   принимается в любом виде — и «имя.vercel.app», и ссылка на `/api/ai`, и
   ссылка на прокси базы, а мусор не принимается; после одного указания адреса
   находятся и помощник, и гифки, адрес запоминается до следующего запуска и
   проверяется первым; гифка, выбранная на телефоне, уходит живой и
   зашифрованной; в настройках видно, почему поиск гифок не работает, теми же
   словами, что ответил сервис; серверных ключей в браузере не оседает.
13. **Шифрование самих уведомлений**: постоянный образец совпадает байт в байт,
   браузер расшифровывает уведомление своим ключом, каждое шифруется заново,
   подпись VAPID проверяется открытым ключом.
14. **Совместимость со «старой» схемой** базы (только `profiles` и `messages`,
   а также база без колонок каналов, ответов и ключей).
15. **Состояние базы сразу после `schema.sql`**, когда кеш REST-API ещё не
   видит функций входа.

Структура:


## 14. Что было исправлено

Исходный файл `wolffmsg2.html` в рабочее состояние не приводился точечно — логика
переписана, потому что часть ошибок была архитектурной. Основное:

**Не работало по существу**

- список чатов хранился только в `localStorage`: собеседник не видел чат, пока не
  добавлял вас вручную. Теперь чаты и участники лежат в таблице `chats`, а
  локальная копия осталась только как кэш и запасной вариант;
- в открытом чате не было опроса сервера — новые сообщения появлялись лишь после
  отправки своего. Добавлен инкрементальный опрос (новые сообщения, реакции,
  удаления, отметки о прочтении);
- счётчик непрочитанных `f.unread` никогда не заполнялся, а вёрстка галочек
  статуса существовала в CSS, но не использовалась;
- `openReactions` была объявлена дважды: вторая версия перетирала первую и
  вызывала несуществующую `addReaction` — реакции не ставились вообще;
- `toggleChatActions`, `muteChat`, `clearHistory` тоже были продублированы;
- удаление аккаунта обращалось к несуществующей таблице `/users`;
- `openSettings` открывала `#settings-page`, которого нет в разметке (страница
  называется `#page-settings`);
- кнопка регистрации показывала текст «Ещё нет аккаунта? Создать» вместо действия,
  а никнейм при регистрации не проверялся на занятость — появлялись дубликаты;
- `syncData` перерисовывала список, но `setInterval` продолжал работать после
  выхода из аккаунта.

**Надёжность и безопасность**

- текст сообщений и имена подставлялись в `innerHTML` без экранирования — любое
  сообщение с HTML ломало разметку или выполняло код. Теперь всё экранируется, а
  обработчики повешены делегированием вместо `onclick` со строками;
- пароль передавался в строке запроса и хранился открытым текстом. Появились
  функции `wm_register` / `wm_login` / `wm_set_password` с bcrypt; читать колонки
  с паролями клиентскому ключу запрещено на уровне прав;
- любая сетевая ошибка показывала «Ошибка соединения» и возвращала `null`, из-за
  чего вызывающий код падал дальше. Теперь ошибки типизированы, есть
  переподключение, перебор адресов и постоянная плашка о состоянии связи;
- фото уходило в базу целиком в base64 — большие файлы просто не отправлялись.
  Изображения масштабируются до 1280 px и сжимаются в JPEG;
- `me.name.split(...)`, `JSON.parse(localStorage…)` и обращения к элементам
  выполнялись без проверок и роняли скрипт на пустых значениях.

**Из последних правок**

- в чатах попадались нечитаемые «зашифрованные» сообщения. Причина: если оба
  собеседника открывали новый чат одновременно, каждый создавал свой ключ
  комнаты и вторая запись затирала первую — часть сообщений оставалась
  зашифрованной ключом, которого уже ни у кого нет. Теперь при записи ключа
  побеждает тот, кто успел первым, а приложение берёт из базы то, что там
  действительно лежит. Старые нечитаемые сообщения больше не показываются:
  вместо них одна строка «Скрыто N сообщений: они зашифрованы прежним ключом»;

- WolffAI не отвечал: приложение искало сервер только рядом с активным
  адресом базы, а сайт на GitHub Pages работает с сервером на другом домене.
  Теперь помощник ищется рядом со всеми известными адресами, а в настройках
  видно его состояние. Заодно `package.json` перестал исключаться из сборки
  Vercel — без него серверные функции могли не собираться;

- иконка приложения: волк был мелким на большом тёмном поле — теперь занимает
  почти всю картинку (`assets/icon.svg`, пересборка `node tools/make-icons.mjs`);

- в строке состояния телефона вместо волка был белый квадрат: значок
  уведомления телефон рисует одним цветом, беря от картинки только
  прозрачность, а туда отдавалась цветная иконка приложения. Сделан
  отдельный одноцветный силуэт;
- уведомления приходили, только пока приложение запущено. Добавлена
  рассылка через службу доставки браузера (раздел 8): таблица подписок,
  три функции в базе и серверная функция, которая шифрует и подписывает
  уведомления по стандартам RFC 8188/8291/8292;
- ярлык установленного приложения открывал страницу «404»: манифест лежал в
  подпапке `assets/`, а `start_url` и `scope` считаются от адреса самого
  манифеста — приложение запускалось по несуществующему адресу
  `…/assets/`. Манифест перенесён в корень сайта, добавлена страница-спасатель
  `404.html`, а service worker при ответе «404» на переход отдаёт оболочку
  приложения — уже сохранённые ярлыки тоже начинают работать;
- смена пароля не перешифровывала закрытый ключ: на другом устройстве он больше
  не открывался, приложение выдавало новую пару ключей, и вся прежняя переписка
  становилась нечитаемой;
- атрибут `hidden` перебивался `display` из классов, поэтому скрытые блоки
  (например «Ничего не найдено») оставались на экране — добавлено общее правило;
- ссылка вида `?api=` с чужим доменом молча уводила переписку и пароль на
  посторонний сервер; теперь требуется подтверждение с показом домена;
- помощник WolffAI не находился, когда сайт открывали с GitHub Pages: серверные
  функции искались только рядом с адресом базы, а на Pages их нет вовсе. Теперь
  адрес сервера задаётся один раз — полем `serverUrl` в конфигурации или в
  настройках на устройстве, — проверяется первым и запоминается; тем же адресом
  включаются уведомления при закрытом приложении и гифки, а в настройках видно,
  какие адреса были проверены и что там оказалось;
- обновления кода доезжали через один запуск: service worker отдавал `app.js` из
  кэша, а свежую версию подтягивал в фоне. Теперь скрипты и стили берутся из
  сети с коротким ожиданием, а кэш остаётся резервом на случай отсутствия связи.

**Интерфейс**

- CSS содержал по три копии правил для `#context-bar`, `.reaction-picker`,
  `.reaction-badge` и конфликтующие блоки для страниц: `#page-settings` был
  одновременно `display:flex !important` и сдвинут за экран. Стили переписаны без
  дублей, переменная `--panel` определена во всех темах (раньше меню были
  прозрачными в стандартной теме);
- добавлены: разделители дат, автор сообщения в группах, просмотр фото на весь
  экран, многострочный ввод (Enter — отправить, Shift+Enter — перенос), поиск,
  собственные модальные окна вместо `prompt`/`confirm` (они блокируются в части
  мобильных браузеров), аппаратная кнопка «назад», локальные аватары вместо
  запросов к `ui-avatars.com`.

## 15. Ограничения

Приложение обращается к базе публичным ключом `anon`. Содержимое переписки
этим ключом не прочитать — оно зашифровано ключами, которых на сервере нет.
Но у такой схемы есть честные границы:

- **метаданные видны**: кто, когда и в каком чате писал, а также никнеймы,
  имена и аватары;
- **записи можно портить**: владелец ключа может удалить или подменить строки
  в таблицах — подмену текста получатель увидит как нечитаемое сообщение, но
  удаление ничем не остановить;
- **ключ живёт в браузере**: тот, у кого есть доступ к разблокированному
  устройству, прочитает переписку. При выходе из аккаунта ключи стираются;
- **защита от подмены ключей — на вас**: сверяйте код безопасности, иначе
  теоретическая подмена открытого ключа на сервере останется незамеченной.

Следующий шаг для полноценной приватности — Supabase Auth с политиками RLS по
`auth.uid()`, чтобы ограничить и метаданные тоже. Текущая схема к этому готова:
таблицы и связи не изменятся, поменяются политики и способ входа.
